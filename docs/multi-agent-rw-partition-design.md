## 0. 摘要（TL;DR）

多子智能体协作的核心矛盾是：**为了快，要并行；为了对，要串行**。本设计把操作系统内存分区与进程/线程模型迁移到多智能体编排上，给出四个正交的答案：

1. **性质判定**：任何子智能体任务先判定为「只读 / 读写 / 读后写」三态之一，再结合依赖图决定并行还是串行。并行充要条件是「无依赖 **且** 不争用同一可写资源」。
2. **读写分区**：把资源划分为四层 —— **L0 内核区 / L1 只读共享区 / L2 可读写共享区 / L3 私有工作区**。分区即权限：L1 无锁只读，L2 写互斥读共享，L3 完全私有。
3. **并发控制**：混合策略。L1 用类 RCU 的无锁读 + 单调版本校验；L2 用悲观读写锁 + 租约 + 锁排序；L3 无锁。写-写由锁保证互斥，读-读天然并行，读-写由版本号校验兜底。
4. **上下文同步**：每个子智能体的上下文 = **基线快照 B + 增量事件流 E + 私有状态 P + 订阅集合 S**。只读区永不失效；可写区变更通过事件流推送 diff，其他 agent 按需重放，串行 agent 天然基于最新基线。

一致性目标：**L2 线性化（写原子生效、后续读立即可见）+ L1 单调读（同一 agent 不会读到更旧的版本）**。

此外，LLM agent 有一个经典事务没有的能力 —— **语义判断**：它能判断「对方的写是否真的使我的计划失效」，并只修复受影响的操作。因此在硬保证之上叠加一层 **advisory（通告-修复）层**（借鉴 CoAgent 的 MTPO 思想），把「锁/中止」升级为「通告/修复」，从而在正确性与并发度之间取得更好的折中。

## 1. 背景与问题陈述

在一个 IDE 会话里，主会话会派生多个 sub-agent 去完成可并行的子任务（改不同文件、跑不同检索、做不同分析）。这些 agent 共享同一个工作区文件系统。当两个 agent 同时改同一个文件时，就会出现经典竞态：

- **丢失更新（lost update）**：后写覆盖先写，先写结果静默丢失。
- **脏读 / 陈旧上下文（stale read）**：agent 基于旧版本代码推理，得出已失效的结论。
- **写-写交错**：文件内容被交错写入，产生损坏或难解的合并冲突。
- **级联失效**：A 改了接口，B 的计划基于旧接口，错误向下游传播。

传统数据库的并发控制（2PL / OCC）不能直接照搬，原因有三（来自 CoAgent 的观察）：

1. **事务跨度过长**：一个 agent 事务跨越数分钟推理，锁会被持有极长时间。
2. **读集合宽泛且不透明**：agent 的读集合无法静态推断。
3. **写无法 fork / buffer**：IDE 里写文件即刻生效，没有可回滚的中间态。

因此本设计的目标是：**在不牺牲 LLM agent 语义判断能力的前提下，给出可落地、可验证的资源分区与并发上下文规范**。

## 3. 设计原则

| 原则 | 含义 | 来源类比 |
|---|---|---|
| **读写分离** | 先判定读写性质，再决定并发规则 | 读者-写者问题 |
| **写互斥、读共享** | 同一可写资源同时只有一个写者，读者可并行 | RWLock / 2PL |
| **默认不共享，显式共享** | agent 之间默认看不到对方私有状态，共享必须声明 | 进程默认不共享地址空间 |
| **分区即权限** | 资源属于哪一层，就适用哪一层的并发规则 | 内存段属性（r/w/x） |
| **上下文可重建** | 任何 agent 的上下文都能由「基线 + 事件流」重建 | MVCC 多版本 |
| **单调读** | 只读区版本只增不减，agent 不会读到更旧的版本 | 单调读一致性 |
| **通告优先于中止** | 冲突时先通告 agent 语义修复，而非直接锁死或回滚 | CoAgent / MTPO |
| **失败可恢复** | 租约超时回收、幂等重试、检查点 | 进程崩溃恢复 |

## 4. 类比模型：从内核内存布局到多智能体

本设计的方法论是**双类比**：用「虚拟地址空间分区」类比**资源读写分区**，用「进程 vs 线程」类比**agent 的独享与共享边界**。

### 4.1 类比映射表

| 内核概念（图一 + 图二） | 多子智能体类比 | 说明 |
|---|---|---|
| **内核区**（受保护、不可变、全局可见） | **L0 调度器 / 内核**（调度规则、锁表、事件日志、元数据） | 所有 agent 共享、只读、运行期只追加 |
| **共享库的存储映射区**（被多个进程共享、只读） | **L1 只读共享区**（规范、公共知识、被依赖的稳定代码、第三方库） | 多个 agent 共享、只读、版本单调 |
| **只读代码段 text**（可读、可执行、共享） | **L1 的可执行只读知识**（规则、接口契约、可复用的确定性过程） | 可执行、只读、共享 |
| **可读写数据段 data**（已初始化的全局可变状态） | **L2 可读写共享区**（正在修改的代码文件、共享数据结构） | 全局共享、可变、受锁保护 |
| **堆 heap**（动态申请、向高地址增长） | **L2 的动态可写对象**（新建的代码对象、临时共享结构） | 动态增长、可读写 |
| **用户栈 stack**（函数调用、向低地址增长、私有） | **L3 私有工作区**（agent 轨迹、草稿、临时文件、本地缓存） | 每 agent 独享、无锁 |
| **进程 Process**（资源分配基本单位、动态、默认不共享） | **子智能体** | 资源分配与隔离的基本单位 |
| **线程 Thread**（CPU 调度基本单位、轻量、共享父进程资源） | **子智能体内的并发执行流 / 并行子任务** | 共享父 agent 的基线快照与只读区 |
| **PCB（进程控制块）** | **AgentControlBlock** | 状态、权限、持有锁、依赖、基线版本 |
| **TCB（线程控制块）** | **TaskControlBlock** | 一次子任务的执行上下文 |
| **进程独享**（地址空间、打开的文件、信号量） | **agent 独享**（上下文快照、私有文件句柄、私有锁/信号量） | 默认不共享 |
| **线程共享**（虚拟地址空间、代码段、数据段、堆、打开的文件） | **同一 agent 的任务共享**（基线快照、只读区、私有工作区） | 共享父 agent 资源 |
| **切换代价：进程大（换地址空间）/ 线程小（换寄存器）** | **agent 切换贵（重载上下文）/ 任务切换便宜（复用基线）** | 指导并行粒度与缓存策略 |

### 4.2 进程/线程类比的三个关键启示

1. **资源分配基本单位是 agent，调度基本单位是任务。** 正如「进程是资源分配的基本单位、线程是 CPU 调度的基本单位」，本设计中 agent 是**资源与上下文分配**的基本单位，而 agent 内部的子任务/工具调用是**调度**的基本单位。
2. **独享与共享的边界就是并发规则的边界。** 进程独享地址空间 → agent 独享上下文；线程共享地址空间 → 同 agent 任务共享基线。共享得越多，需要协调的锁越多。
3. **切换代价决定并行粒度。** 进程切换要换整个地址空间（昂贵），线程切换只换寄存器（廉价）。类比到 agent：跨 agent 切换要重载上下文（昂贵），agent 内任务切换复用基线（廉价）。因此**应尽量减少 agent 数量、提高单 agent 内的任务并行度**。

## 5. 资源四层分区模型（L0–L3）

### 5.1 总览图

```
                        多子智能体资源分区（类比虚拟地址空间）
  ┌──────────────────────────────────────────────────────────────────────┐
  │ L0  内核区 Kernel                                                     │
  │     调度规则 · 锁表 · 事件总线 · 元数据     [全局共享 · 只读 · 只追加]   │
  ├──────────────────────────────────────────────────────────────────────┤
  │ L1  只读共享区 Shared-RO   （类比 共享库映射区 + 只读代码段 text）        │
  │     规范 · 公共知识 · 被依赖代码 · 接口契约   [全局共享 · 只读 · 版本单调] │
  ├──────────────────────────────────────────────────────────────────────┤
  │ L2  可读写共享区 Shared-RW  （类比 数据段 data + 堆 heap）               │
  │     正在修改的代码 · 共享数据结构              [受锁保护 · 线性化]         │
  ├──────────────────────────────────────────────────────────────────────┤
  │ L3  私有工作区 Private      （类比 用户栈 stack）                        │
  │     agent-A 轨迹/草稿      agent-B 轨迹/草稿      ...   [独享 · 无锁]    │
  └──────────────────────────────────────────────────────────────────────┘
        ↑ 高地址（内核/受保护）                              ↑ 低地址（私有/用户）
```

### 5.2 L0 内核区（Kernel）

- **内容**：调度规则、锁表、事件总线、任务依赖图、AgentControlBlock 表、审计日志。
- **访问权限**：全局共享、**只读**（运行期只追加、不修改既有条目）。
- **并发规则**：无锁读；结构变更由调度器单线程串行化（类比内核单线程持有大锁）。
- **生命周期**：会话级，随会话创建/销毁。
- **典型内容**：`Scheduler`、`LockTable`、`EventBus`、`AgentRegistry`。

### 5.3 L1 只读共享区（Shared-RO / text）

- **内容**：编码规范、架构约定、公共知识、**被依赖且稳定的代码**、第三方库、接口契约（未变动部分）。
- **访问权限**：全局共享、**只读**。
- **并发规则**：**无锁读**；读取时记录版本号，写入（升级/重新生成）需独占。
- **版本语义**：**单调递增**（monotonic）。旧版本可保留一段时间供在途读者使用，之后回收（类比 RCU 宽限期）。
- **生命周期**：跨任务长期存在，按版本演进。
- **典型内容**：`spec.md`、`README`、`interfaces/`、`vendor/`、公共工具函数。

### 5.4 L2 可读写共享区（Shared-RW / data + heap）

- **内容**：**正在被修改的代码文件**、共享数据结构、任务产出物、接口契约（变动部分）。
- **访问权限**：全局共享、**可读写**。
- **并发规则**：**悲观读写锁**（写互斥、读共享）+ **租约**（lease）+ **超时**；支持锁升级/降级、按路径前缀加锁。
- **版本语义**：每次成功写产生**新版本**，线性化（写原子生效）。
- **生命周期**：任务级，随任务开始进入、提交后升级或释放。
- **典型内容**：`src/**` 中被改的文件、`package.json`、共享配置。

### 5.5 L3 私有工作区（Private / stack）

- **内容**：agent 的执行轨迹、推理草稿、临时文件、本地缓存、中间结果。
- **访问权限**：**仅该 agent 可见**（独享）。
- **并发规则**：**无锁**（无其他 agent 访问）。
- **版本语义**：无需版本（或仅本地单调）。
- **生命周期**：agent 级，agent 结束即回收；可按需持久化为检查点。
- **典型内容**：`.agents/<id>/scratch/`、`.agents/<id>/trajectory/`。

### 5.6 分区属性矩阵

| 层 | 共享范围 | 读写 | 并发机制 | 版本语义 | 失效方式 | 可丢弃 |
|---|---|---|---|---|---|---|
| L0 内核区 | 全局 | 只读 | 无锁读 / 单写者串行 | 只追加 | 不变 | 否 |
| L1 只读共享区 | 全局 | 只读 | 无锁读 + 版本校验 | 单调递增 | 永不失效 | 否 |
| L2 可读写共享区 | 全局 | 读写 | 读写锁 + 租约 | 线性化 | 事件失效 | 否 |
| L3 私有工作区 | 单 agent | 读写 | 无锁 | 本地单调 | agent 内失效 | 是 |

### 5.7 资源分区判定流程

给定一个资源（文件/目录/数据结构），按下述决策树判定其归属层级：

```
资源是否属于调度规则/锁表/事件日志/元数据？
  ├─ 是 → L0
  └─ 否 → 该资源在本次任务中是否会被写入？
        ├─ 否（只读）→ 它是否被多个 agent 共享？
        │     ├─ 是 → L1
        │     └─ 否 → L3（无共享需求，放私有区即可）
        └─ 是（会写）→ 它是否被多个 agent 共享？
              ├─ 是 → L2
              └─ 否 → L3（单写者，无需共享锁）
```

**关键推论**：判定结果直接决定并发开销。只读且共享 → 无锁；可写且共享 → 必须加锁。因此**在设计任务时，应尽量把「稳定、被依赖」的资源固化到 L1，把「正在改」的资源隔离到尽量小的 L2 集合**。

## 6. 任务性质判定：并行还是串行

### 6.1 读写性质三态

每个任务对其涉及的每个资源，必须先声明访问模式：

| 性质 | 定义 | 并发含义 |
|---|---|---|
| **只读（read）** | 只观察，不改变资源 | 可与其他读并行 |
| **读写（write）** | 会改变资源 | 与其他写互斥；与读需版本校验 |
| **读后写（read-modify-write）** | 先读后写（如追加、计数、重构） | 等价于写，且需防止丢失更新 |

> 注意：**「读后写」必须按写处理**。这是读者-写者问题里最容易被忽视的一点 —— 生产-消费者模型中的消费者看似在「读」，实则改变了共享状态（计数、指针），因此它也是写者。

### 6.2 并行判定谓词

两个任务 `a`、`b` 可并行的**充要条件**：

```
canRunInParallel(a, b) :=
      (a 不依赖 b) 且 (b 不依赖 a)          // 控制/数据依赖
  且  (a.writes ∩ b.writes = ∅)             // 不写同一资源
  且  (a.writes ∩ b.reads  = ∅) 或 允许陈旧读  // 写-读冲突（默认不允许）
  且  (a.reads  ∩ b.writes  = ∅) 或 允许陈旧读
```

前两条是硬条件；后两条取决于一致性要求：

- **严格模式（默认）**：写-读冲突也禁止并行 → 完全线性化，最安全。
- **宽松模式**：允许读旧版本（单调读保证），写-读可并行 → 并发度高，但读者可能基于陈旧上下文，需靠版本校验在提交前拦截。

### 6.3 依赖图与分层调度

把任务组织为 DAG：节点 = 任务，边 = 依赖（`a → b` 表示 b 依赖 a 的产出）。

- **同一层（无依赖）的任务**：用 6.2 谓词两两判定，可并行的组成一个并行组。
- **不同层**：必须串行（屏障 barrier 隔开）。
- **部分独立**：B、C 都依赖 A 但彼此独立 → 先 A，再并行 B、C。总耗时 = t(A) + max(t(B), t(C))。

### 6.4 并行度上界

```
最大并行度 = min( 当前层无冲突任务数 , 可写资源分区数 , 并发预算 )
```

- **无冲突任务数**：由依赖图与资源冲突决定。
- **可写资源分区数**：L2 被划分的独立可写单元数（不同文件 = 不同单元）。
- **并发预算**：成本/限流/上下文窗口预算，是人为上限。

## 7. 并发控制：混合策略

### 7.1 各层并发规则一览

| 层 | 读 | 写 | 机制 |
|---|---|---|---|
| L1 | 无锁 | 独占（升级） | 版本号 + 宽限期 |
| L2 | 共享锁 | 排他锁 | 读写锁 + 租约 |
| L3 | 无锁 | 无锁 | 无 |

### 7.2 L1：无锁读 + 版本校验（RCU 思想）

L1 的读远多于写（读:写 常达 10:1 以上），适合 RCU 式处理：

- **读者**：无锁访问，记录开始时的版本号 `v_start`；临界区结束校验版本仍为 `v_start`，否则重试。
- **写者**：复制-修改-原子替换（copy-modify-swap），产生新版本 `v+1`；旧版本进入**宽限期**，等所有 `v_start ≤ v` 的在途读者退出后再回收。

```
function l1_read(resource):
    v = resource.version
    snapshot = resource.data
    result = use(snapshot)
    if resource.version != v:
        return RETRY
    return result
```

**为什么不用普通 RWLock**：RWLock 的读者也要取共享锁，触发原子操作与缓存行失效；RCU 把锁从读路径彻底移除，读性能可提升一个数量级。

### 7.3 L2：悲观读写锁 + 租约

L2 是并发冲突的主战场，采用**悲观读写锁**（写互斥、读共享）：

- **读锁（S）**：可多个 agent 同时持有。
- **写锁（X）**：排他，持有期间无任何其他锁。
- **锁兼容矩阵**：S 与 S 兼容；S 与 X、X 与 X 均不兼容。

```
function rwlock_acquire(lock, mode, agent):
    while not compatible(lock.held, mode):
        if lock.lease_expired(lock.holder):
            force_release(lock)
            continue
        enqueue(lock.waiters, agent, mode)
        block(agent)
    lock.held.add(mode, agent)
    lock.lease[agent] = now() + LEASE_MS

function rwlock_release(lock, agent):
    lock.held.remove(agent)
    grant_waiters(lock)
```

**租约（lease）机制**：写锁不是无限持有的。每个锁带超时 `LEASE_MS`；若持有者崩溃/卡死，租约到期后调度器强制回收，避免死锁永久化。这与「agent 事务跨分钟级推理」的场景高度相关 —— 必须有超时兜底。

### 7.4 锁粒度与锁表

- **粒度选择**：文件级（简单、并发度低）→ 目录级（中等）→ 块/区域级（高并发、实现复杂）。
- **建议默认**：**文件级**，配合**路径前缀加锁**（改 `src/a/b.ts` 时锁 `src/a/b.ts`，检索时可锁 `src/` 前缀做粗粒度串行化）。
- **锁表**：调度器维护全局锁表 `resource_path → {held_modes, waiters, lease}`。

### 7.5 死锁预防与饥饿避免

| 问题 | 机制 |
|---|---|
| **死锁** | ① **锁排序**：所有 agent 按资源路径字典序加锁，禁止逆向；② **一次性申请**（all-or-nothing）：一次申请全部所需锁，否则全不持有；③ 超时回退重试 |
| **饥饿** | 写者优先 / FIFO 公平队列；避免写者被源源不断的读者饿死 |
| **锁升级死锁** | 升级（S→X）前检查是否会与其他持有者冲突，冲突则先释放再重试 |

### 7.6 乐观路径（可选）

对**低冲突**资源（如各 agent 只写自己独占的文件），可走乐观并发：

- 每资源带单调版本号；写时用 CAS（compare-and-swap）提交。
- 冲突则回滚重试，或用**三路合并**（three-way merge，基于共同祖先）自动合并。

### 7.7 单写者模式（Single-Writer）

对同一可写资源，采用**单写者语义**：指定一个 owner agent 拥有写权限，其他 agent 只能**提议补丁（patch proposal）**，由 owner 执行实际写入。

- 优点：写并发度严格为 1，语义最简单，杜绝写-写交错。
- 缺点：owner 成为瓶颈。
- 适用：高频变动的核心文件、共享配置。

### 7.8 语义修复层（Advisory / MTPO 思想）

硬保证（锁/版本）解决「不冲突」，但 LLM agent 有独特能力：**判断冲突是否真的使自己的计划失效**。因此叠加 advisory 层：

- **通告（notify）**：当资源变更时，运行时通知受影响的 reader，告知「你依赖的版本 v 已变为 v+1，diff 如下」。
- **修复（repair）**：reader 自己判断该 diff 是否影响其计划；若影响，只重做受影响的步骤，而非整个任务重来。
- **兜底**：无法语义修复时，回退到锁/中止。

这正是 CoAgent 的核心结论：2PL 在 10 个争用负载上仅 1.04× 加速且每次试验 0.81 次死锁，OCC 因中止反而 0.93×（更慢）且 token 成本 1.83×，而 advisory 的 MTPO 达到 1.40× 加速、零中止、token 成本仅 1.15×。**对 LLM agent 而言，「通告-修复」优于「锁-中止」。**

## 8. 上下文模型

### 8.1 上下文构成

每个子智能体的上下文由四部分组成：

```
C_agent = ( B , E , P , S )

B = 基线快照   Baseline   ：任务开始时 L1 + 可读 L2 资源的版本化副本
E = 增量事件流 Event Log  ：任务期间订阅到的资源变更事件（diff/操作）
P = 私有状态   Private    ：轨迹、草稿、中间结果（对应 L3）
S = 订阅集合   Subscriptions：该 agent 关心的资源集合（决定收到哪些事件）
```

### 8.2 基线快照 B

- 任务启动时，从 L1 与可读的 L2 资源抓取**版本化副本**，记录 `baseline_version`。
- B 是**不可变**的（对应内存的只读快照），agent 推理期间不改变。
- B 决定了 agent 的「认知起点」。

### 8.3 增量事件流 E

- 任务期间，凡 agent 订阅的 L2 资源发生变更，事件进入 E。
- 每个事件结构见 §9.1。
- E 是**追加式**的，可重放（replay）—— 这是「上下文可重建」原则的基础。

### 8.4 订阅集合 S

- agent 根据任务需要声明订阅（如「我读了 `src/a.ts`，订阅它的变更」）。
- S 决定 agent 收到哪些事件，**最小化无关干扰、控制上下文体积**。
- 订阅可动态增减。

### 8.5 私有状态 P

- agent 独占（L3），不参与共享并发控制。
- 可按需持久化为检查点（checkpoint），支持崩溃恢复。

### 8.6 上下文计算时机与算法

**四个时机**：

1. **任务开始**：构建 B，初始化 E/P/S。
2. **收到事件**：把事件追加到 E，标记受影响的上下文块为 `stale`。
3. **使用前校验**：agent 即将使用某资源前，检查其版本；若 `stale` 则重放 E 或拉取最新。
4. **显式刷新**：agent 主动请求重建上下文。

**上下文重建算法**：

```
function rebuild_context(agent):
    fresh = {}
    fresh.P = load_private_state(agent)
    fresh.B = snapshot_baseline(agent.baseline_version)
    for event in replay(agent.E, from = agent.consumed_offset):
        if event.resource in agent.S:
            apply_diff(fresh.B, event.diff)
            mark_dependent_blocks(agent, event, STALE)
    agent.consumed_offset = agent.E.tail
    return fresh
```

**只读区永不失效**：L1 版本单调，agent 的 L1 快照永远有效，无需重放。这是把「稳定资源固化到 L1」的收益 —— **直接省去大量失效重算**。

### 8.7 上下文大小控制

上下文窗口有限，必须控制体积：

- **分层加载**：先给摘要/索引，按需展开详情（类比虚拟内存按需分页）。
- **懒加载**：只在实际访问某资源时才拉取其内容。
- **裁剪（pruning）**：丢弃已被后续事件覆盖的旧事件、已完成的中间结果。
- **压缩**：对历史事件做摘要，保留语义、丢弃细节。

## 9. 变更传播与失效机制

### 9.1 事件模型

```
Event = {
    id         : 全局唯一单调 id
    resource   : 变更的资源路径（L2）
    type       : CREATE | MODIFY | DELETE | RENAME
    version    : 变更后的新版本号
    diff       : 结构化差异（而非全文，节省 token）
    producer   : 产生变更的 agent id
    timestamp  : 逻辑时钟 / 物理时间
}
```

> **用 diff 而非全文**：LLM 上下文昂贵，传 diff 可大幅降低 token 成本。

### 9.2 发布订阅

- **发布者**：写者在 L2 成功提交写时，向事件总线发布 Event。
- **订阅者**：事件总线根据各 agent 的 S，把事件路由到对应 agent 的 E。
- **串行 agent**：天然按顺序消费，后来者基于最新基线，无需复杂重放。

### 9.3 并行 agent 的响应

```
并行场景：A、B 同时读 R（版本 v），随后 C 写 R（版本 v+1）

1. C 取 R 的写锁，提交，发布 Event{resource:R, version:v+1, diff}
2. 事件总线通知 A、B（它们订阅了 R）
3. A、B 的 E 追加该事件，R 相关上下文块标记 STALE
4. A、B 下次使用 R 前：
     - 若已结束 → 无需处理
     - 若仍在进行 → 重放 diff 更新本地视图，或拉取 v+1 重新推理受影响部分
5. 若 A、B 无需再写 R → 无冲突
   若 A 或 B 也要写 R → 写锁已被 C 持有，进入等待/串行化
```

### 9.4 串行 agent 的响应

串行（有依赖边）场景下，后续 agent 在前置 agent **提交之后**才启动：

- 它的基线快照 B 直接建立在最新版本上，天然一致。
- 屏障（barrier）保证前置产出已落盘/已提交。

### 9.5 冲突处理矩阵

| 冲突类型 | 触发条件 | 处理机制 |
|---|---|---|
| 写-写 | 两 agent 写同一 L2 资源 | 写锁互斥 → 串行化；或单写者模式 |
| 读-写 | 读者持旧版本，写者发布新版本 | 版本校验 + 事件失效 + 按需重放 |
| 读-读 | 多读者读同一资源 | 无冲突，天然并行 |
| 丢失更新 | 读后写未检测到并发修改 | 版本号 CAS；冲突则重试/三路合并 |
| 级联失效 | 上游改动使下游计划失效 | 依赖图 + 事件传播 + advisory 修复 |

## 10. AgentControlBlock（PCB 类比）

### 10.1 字段

```
AgentControlBlock = {
    id              : agent 唯一标识
    state           : CREATED | READY | RUNNING | BLOCKED | DONE | FAILED
    baseline_version: 基线快照对应的版本号
    subscriptions   : 订阅的资源集合 S
    held_locks      : 持有的锁集合（含租约到期时间）
    dependencies    : 依赖的任务/agent 集合
    private_ws      : 私有工作区指针（L3）
    read_set        : 已读资源及版本（用于冲突检测）
    write_set       : 已写资源及版本（用于提交校验）
    budget          : 并发/成本/上下文预算
    checkpoint      : 最近检查点
}
```

> `read_set` / `write_set` 合称 agent 的 **state footprint**（状态足迹）—— 它既是并发检测的依据，也是上下文重建的依据。

### 10.2 生命周期状态机

```
CREATED ──dispatch──▶ READY ──schedule──▶ RUNNING
                                           │
                          wait(lock)───────┤
                          ▼                 │
                       BLOCKED ──grant──────┘
                                           │
                          success ──────────┤
                          ▼                 ▼
                          DONE           FAILED
                                           │
                          retry ────────────┘
```

- **BLOCKED**：等待锁/依赖。必须带超时（租约），超时转 FAILED 或重试。
- **FAILED**：释放全部锁、回收租约、持久化检查点，可重试。

## 11. 调度器（内核区）

### 11.1 职责

调度器是 L0 的实体，类比内核：

1. **任务分派**：按依赖图拓扑排序 + 资源冲突检测，决定并行组与执行顺序。
2. **锁管理**：维护全局锁表，处理申请/授予/超时回收。
3. **事件总线**：路由变更事件到订阅者。
4. **死锁检测**：维护等待图（wait-for graph），检测环并触发回退。
5. **配额与限流**：并发预算、成本上限。
6. **审计**：记录全部锁与事件日志（L0 只追加）。

### 11.2 调度算法

```
function schedule(tasks):
    layers = topological_layers(tasks)        // 按依赖分层
    for layer in layers:
        parallel_group = []
        for task in layer (按优先级):
            if all(canRunInParallel(task, member) for member in parallel_group):
                parallel_group.add(task)
            else:
                defer(task)                   // 推到下一批
        dispatch_parallel(parallel_group)     // fork
        barrier_wait_all(parallel_group)      // join
    return
```

### 11.3 屏障与阶段

- **屏障（barrier）**：每层结束后等待全部任务完成，保证下一层基于一致状态启动。
- **阶段（phase）**：把大任务划分为若干阶段，阶段间串行、阶段内并行。

### 11.4 失败与恢复

| 故障 | 恢复机制 |
|---|---|
| agent 崩溃 | 租约超时回收锁；从检查点重试 |
| 死锁 | 等待图检测 → 回退代价最小的任务 |
| 部分失败 | 幂等重试；失败任务隔离，不阻塞全局 |
| 事件丢失 | 事件日志持久化 + 偏移量重放 |

## 12. 一致性与正确性

### 12.1 一致性目标

| 层 | 目标 | 语义 |
|---|---|---|
| L2 | **线性化（Linearizability）** | 写原子生效；任何后续读立即看到最新值 |
| L1 | **单调读（Monotonic Read）** | 同一 agent 不会读到比之前更旧的版本 |
| L3 | 本地单调 | 仅 agent 自己可见 |

### 12.2 不变量（Invariants）

1. **写互斥**：同一 L2 资源任意时刻至多一个写锁持有者。
2. **读共享**：L1 读、L2 读锁均可多 agent 并行。
3. **无死锁**：锁排序 + 超时保证系统总能推进。
4. **上下文可重建**：任意 agent 上下文可由 `(B, E)` 重建。
5. **事件不丢**：每个成功写都产生且仅产生一个可投递事件（幂等）。
6. **单调版本**：所有资源版本号单调递增，不回退。

### 12.3 竞态场景与处置

| 场景 | 风险 | 处置 |
|---|---|---|
| 两 agent 同改一文件 | 丢失更新/交错写 | 写锁互斥（§7.3）/ 单写者（§7.7） |
| 一读一写同文件 | 脏读 | 版本校验 + 事件失效（§9.3） |
| 读后写未检测并发 | 丢失更新 | 版本 CAS + 三路合并（§7.6） |
| 循环等待锁 | 死锁 | 锁排序 + all-or-nothing（§7.5） |
| 写者持锁崩溃 | 永久死锁 | 租约超时回收（§7.3） |
| 上游改接口下游不知 | 级联失效 | 依赖图 + 事件传播 + advisory（§7.8） |

## 13. 场景走查（Walkthrough）

**场景 A：3 个 agent 并行改 3 个不同文件**
- 资源分属 3 个独立 L2 单元，`writes ∩ = ∅`，无依赖 → **全并行**。
- 并行度 = 3。无锁冲突。

**场景 B：2 个 agent 同时改同一文件**
- `writes ∩ ≠ ∅` → 不可并行。写锁互斥 → **串行化**（后到者等待）。
- 或单写者模式：另一 agent 提 patch proposal。

**场景 C：1 个 agent 改代码，另 1 个正在读该代码**
- 读者基线 v，写者发布 v+1 → 读者 E 追加事件，相关块 STALE → 按需重放或重读。
- 若读者接下来也要写 → 需先取写锁（可能被写者持有 → 等待）。

**场景 D：agent 改代码，串行后续 agent 依赖该改动**
- 依赖边 → 屏障隔开 → 后续 agent 基线直接建立在 v+1 → **天然一致**。

**场景 E：两 agent 循环等待对方的锁**
- 锁排序（按路径字典序）禁止逆向加锁 → **不可能成环**；或 all-or-nothing 一次性申请避免部分持有。

**场景 F：agent 崩溃**
- 租约超时 → 调度器强制回收其锁 → 其他 agent 得以推进；崩溃 agent 从检查点重试。

## 14. 权衡与边界

| 维度 | 取舍 | 建议 |
|---|---|---|
| **锁粒度** | 粗（简单、并发低）vs 细（复杂、并发高） | 默认文件级 + 路径前缀 |
| **悲观 vs 乐观** | 悲观（可预测、可能死锁）vs 乐观（高并发、冲突处理复杂） | L2 悲观、L1 无锁、低冲突资源乐观 |
| **一致性 vs 性能** | 强一致（慢）vs 弱一致（快） | L2 线性化、L1 单调读 |
| **上下文完整性 vs token 成本** | 全量（准、贵）vs 增量（省、可能漏） | 基线 + 事件流增量 + 分层加载 |
| **并行度 vs 预算** | 高并行（快、贵）vs 低并行（省、慢） | 并发预算硬上限 |
| **OT vs CRDT**（语义合并时） | OT 集中式、需正确转换函数；CRDT 去中心化、元数据开销大 | agent 场景倾向 OT（有中心调度器） |

**已知局限**：

- 本规范假设**单工作区、单调度器**；跨机器分布式事务不在范围内。
- LLM 推理的**非确定性**意味着「相同输入不保证相同输出」，语义修复层只能缓解、不能根除。
- 超大仓库下，事件流与基线快照的存储/传输成本需专门优化（分层加载、裁剪）。
- 上下文窗口是硬约束，长任务必须裁剪，可能丢失细节。

## 15. 验收标准（Checklist）

- [ ] 任意资源都能按 §5.7 判定到 L0–L3 之一。
- [ ] 任意两任务的并行/串行判定可用 §6.2 谓词机械执行。
- [ ] L1 读路径无锁；L2 写互斥、读共享；L3 无锁 —— 有对应测试。
- [ ] 写-写冲突被串行化，无丢失更新（测试：两 agent 同改一文件，最终结果确定）。
- [ ] 读-写冲突触发事件失效，读者上下文被正确更新（测试：读者提交前版本校验拦截陈旧提交）。
- [ ] 死锁场景在 `LEASE_MS` 内被自动解除（测试：故意循环等待）。
- [ ] 崩溃 agent 的锁被回收，系统继续推进（测试：kill 写者）。
- [ ] 任意 agent 上下文可由 `(B, E)` 重建（测试：重放事件流得到等价上下文）。
- [ ] 版本号全局单调递增，无回退。
- [ ] 事件投递幂等，重复投递不产生副作用。
- [ ] L2 写线性化：写返回后，任何读立即看到新值。
- [ ] L1 单调读：同一 agent 不会读到比之前更旧的版本。
- [ ] 并发度不超过预算上限。

| 订阅集合 S | agent 关心的资源集合 |
| AgentControlBlock | agent 的控制块（类比 PCB） |
| state footprint | agent 读/写过的资源集合 |
| 租约 lease | 锁的超时持有权，到期可被强制回收 |
| 宽限期 grace period | RCU 中等待在途读者退出的窗口 |
| advisory | 通告-修复式的软并发控制（非锁/中止） |
