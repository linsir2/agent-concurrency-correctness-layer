## 0. 结论摘要

**计网是我们至今找到的最完整的对照系。** 它回答的正是我们最关心的三个问题：

| 我们的问题 | 计网的对应 | 成熟答案 |
|---|---|---|
| **信息有效性（不被流程丢失）** | 可靠传输（ARQ/序号/确认/重传）+ 差错控制 | 停等 / GBN / 选择重传；CRC/海明码 |
| **保持高信息密度** | 信道利用率、信源编码、帧格式 | 增大窗口/有效载荷、压缩、减小头部 |
| **怎么传递数据** | 封装 / PDU / 路由 / 交换 / 多路复用 | 分层封装、存储转发、统计复用 |

**四条最有价值的迁移**：

1. **「乐观基线 + 恢复机制」**（best-effort 叠加可靠性）—— 核心最小，正确性按需叠加。
2. **FEC / ARQ 二分法** —— 映射为「乐观并发/推测执行」与「悲观锁/冲突重试」，是并发正确性层最直接的算法选择框架。
3. **端点决策 + 中间提供信号**（端到端拥塞控制 + ECN）—— **机械一致性**在共享层，**语义正确性**在独立验证器；中间层只提供冲突/版本/时序信号。
4. **CSMA/CD 的「冲突检测 + 指数退避」** —— 直接对应我们的「乐观并发 + 冲突回滚 + 指数退避重试」。

## 1. 核心类比：多智能体分发 = 寄快递

计网教材常用「寄快递」类比（本文引自用户提供的计网导论图片；亦见 Kurose & Ross 的「信封/分层」类比）：

| 寄快递（计网原话） | 多智能体分发 |
|---|---|
| 「你写的信（应用层数据）」 | 用户输入的任务目标 |
| 「打包」 | 任务封装（footprint + 契约） |
| 「贴单」 | 贴上元数据（地址/序号/版本/租约） |
| 「运输」 | 分发与路由 |
| 「分拣」 | 调度与准入 |
| 「送到对方手上」 | 投递给目标 agent / 提交到共享状态 |
| 「货车能跑多快、箱子多大」（物理层） | agent 的执行速率、消息/上下文的容量上限 |
| 「同一小区里挨家送信怎么防丢、防两家同时喊话」（数据链路层） | **多 agent 并发写同一共享资源的冲突与丢失**（正是我们的核心问题） |

> **关键洞察**：计网的数据链路层解决「**同一共享信道上的多路访问 + 差错 + 可靠**」，与我们的「**同一共享工作区上的多路写入 + 冲突 + 正确性**」是**同一问题的两个实例**。

## 2. 分层对照：网络协议栈 ↔ 多智能体协议栈

### 2.1 分层映射

| 网络层 | 职责 | 多智能体对应 | 我们的组件 |
|---|---|---|---|
| **应用层** | 应用间通信规则 | 任务语义、agent 契约 | Planner、ResultEnvelope |
| **表示层** | 格式转换、压缩、加密 | 上下文序列化、压缩、脱敏 | ContextAssembler、Renderer |
| **会话层** | 建立/管理/终止会话 | Run 生命周期、会话 | RunCoordinator |
| **传输层** | 端到端可靠投递、分用 | **消息可靠传递（不丢/不重/有序）** | EventLog（WAL + 全局 seq）、SubscriptionRegistry（按 `(resource, version)` 单调投递）、cursor 水位线（**已具备，非新增**） |
| **网络层** | 逻辑寻址、路由、转发 | **分发路由（哪个 agent 处理哪个任务）** | Dispatcher、Scheduler |
| **数据链路层** | 成帧、MAC、介质访问、差错检测 | **单跳协调（agent ↔ 共享资源）** | IntentRegistry、WorkspaceManager（RSC） |
| **物理层** | 比特传输、介质 | 沙箱/容器、文件系统、网络出口 | P0 底座 |

### 2.2 封装 ↔ 消息生命周期

```
应用层  任务 M
   │  +契约头（目标/验收/预算）
传输层  可靠消息（序号 + 幂等键 + 租约）
   │  +路由头（agent 地址/资源 ID）
网络层  分发分组（任务 ID + 优先级 + footprint）
   │  +帧头帧尾（版本 + CRC + 锁信息）
链路层  资源帧（写意图 + base_version + fencing）
   │  → 提交（原子替换 + 事件）
物理层  沙箱/文件系统操作
```

**中间节点只需理解「窄腰层」的头部**（类比 IP）—— 我们的**资源提交层**就是窄腰：IntentRegistry + WorkspaceManager 只需读「资源 ID + 版本 + 租约」，不需要理解上层任务语义。

## 3. 信息有效性：怎么不被流程走动中丢失

### 3.1 计网的答案：可靠传输（ARQ）

| 机制 | 解决什么 | 原理 |
|---|---|---|
| **序号** | 乱序、重复 | 按字节流编号；接收方据此排序去重 |
| **累积确认** | 反馈开销 | ACK=n 表示 n 之前全部收到（水位线推进） |
| **超时重传** | 丢包 | 未收到 ACK 则重传 |
| **快速重传** | 避免等满 RTO | 收到 3 个重复 ACK 立即重传 |
| **ARQ 协议** | 效率 vs 复杂度 | 停等 / 后退 N 帧 / 选择重传 |

### 3.2 迁移到多智能体

我们的「信息不丢」问题分三类：

| 丢失场景 | 计网对应 | 我们的机制 |
|---|---|---|
| **事件丢失**（写成功但事件未达） | 丢包 | EventLog 的 WAL + 提交事务内追加（同事务，I8） |
| **事件重复**（重试导致重复投递） | 重复分组 | 事件 `id` 去重 + 幂等 apply |
| **上下文陈旧**（读到旧版本） | 旧序号分组的迟到/重传 | 版本校验 + 读集合校验（`REJECT_STALE_READ`） |
| **agent 崩溃丢失进度** | 连接中断 | checkpoint + 重放（`turn_seq` 持久化） |
| **副作用重复** | 重传导致重复 | EffectJournal + `idem_key` 去重 + UNKNOWN 对账 |

**关键迁移**：

```
EventLog 全局 seq → 排序序号（排序/去重）
cursor             → 累积确认（事件消费水位线）
logical_action_id  → 幂等键基准（重传标识，非排序序号）
租约超时 + 重试     → 超时重传
版本冲突立即 rebase → 快速重传（不等下一轮）
ARQ 三协议          → 停等（单写者）/ GBN（有序日志）/ SR（只补缺失）
```

> **核心洞察**：TCP 的可靠性是 **at-least-once**（重传可能重复），不是 exactly-once。**我们也是**：EffectJournal 的 `idem_key` 把「至少一次」变成「效果恰好一次」。这与 LIMBO 的结论一致（幂等键把重复率 28%→4%）。

### 3.3 序号空间约束 ↔ 版本回绕

计网：GBN 要求 `W_T ≤ 2ⁿ−1`，SR 要求 `W_T + W_R ≤ 2ⁿ`，否则「旧重传帧被误认为新帧」。

我们：**版本号/epoch 回绕**是同一问题 —— 有限位数的版本号在回绕后，旧的未确认写可能被误认为新写。

**迁移**：用**单调递增 + 足够位数**（如 64 位 seq），并配合租约（类似 MSL）让旧版本自然消亡。

## 4. 高信息密度：信道利用率与信源编码

### 4.1 计网的答案

**信道利用率**：

```
停等：U = Tf / (Tf + RTT)
滑动窗口：U = (W_T · Tf) / (Tf + 2Tp)
```

提高利用率的手段：**增大窗口**、**增大有效载荷**、**减小 RTT**、**减小头部开销**。

**线路编码**（line coding，非压缩）：曼彻斯特编码牺牲带宽换自同步（每比特必有一次跳变）；差分曼彻斯特用「位首是否跳变」表数据。

**调制**：QAM 用星座点数换比特率（受信噪比限制）。

**信源编码**（source coding，压缩）：去除冗余，如霍夫曼、LZ。

**物理层极限**：奈奎斯特（码元速率上限 `2W`）+ 香农（比特率上限 `W·log₂(1+S/N)`）。

### 4.2 迁移到多智能体：token 就是带宽

| 计网概念 | 多智能体对应 |
|---|---|
| **带宽** | token 预算 / 上下文窗口 |
| **信道利用率** | **信息密度**：有效信息 / token 消耗 |
| **有效载荷 / 帧长** | 消息中「真正有用的内容」占比 |
| **头部开销** | 元数据（地址/序号/版本/租约） |
| **RTT** | agent 往返延迟（模型推理 + 工具执行） |
| **线路编码** | 逻辑序号 + 版本（自同步的「逻辑版」） |
| **信源编码（压缩）** | 上下文摘要 + 分层加载（语义版压缩） |

**关键迁移**：

1. **头部最小化**：消息/事件的元数据要精简。计网用「IPv4 变长首部（含选项最大 60B）→ IPv6 固定 40B + 扩展首部」来**降低逐包解析成本**（注意：IPv6 首部长度其实**更大**，设计目标是「固定头 + 简化」，不是「压缩」）。我们的 `Event` 已用 diff 而非全文 —— 继续压缩元数据字段，并把可选元数据外挂。
2. **增大有效载荷**：一次往返传递尽可能多的有效信息（批量提交 `commit_batch` 就是「增大帧长」）。
3. **减小 RTT**：减少 agent 往返次数（本地决策优先，避免不必要的协调往返）。
4. **压缩**：上下文分层加载 + 摘要（信源编码的语义版）。
5. **提高信噪比**：减少无关事件（订阅过滤 = 降噪），提高「有效信息 / 总 token」比。

> **核心洞察**：**token 是我们的带宽，上下文窗口是我们的信道容量**。设计目标应是「在给定 token 预算下最大化有效语义吞吐」—— 这与计网的「给定带宽下最大化有效吞吐量」完全同构。

## 5. 数据传递：封装 / PDU / 路由 / 交换

### 5.1 计网的答案

- **封装**：每层加上本层头部（+ 尾部），上层 PDU 作为本层载荷。
- **PDU**：物理层=比特、链路层=帧、网络层=分组、传输层=报文段/数据报。
- **路由**：距离向量（RIP）/ 链路状态（OSPF）/ 路径向量（BGP）。
- **交换**：电路交换 / 报文交换 / 分组交换；交换机每端口独立冲突域。
- **多路复用**：FDM/TDM/CDM。

### 5.2 迁移到多智能体

| 计网概念 | 多智能体对应 | 我们的机制 |
|---|---|---|
| **封装** | 任务 → 计划 → 消息 → 事件 的层层包装 | footprint → Plan → Event → ResultEnvelope |
| **PDU** | 逻辑消息单元 | Event（WorkspaceEvent / EffectEvent） |
| **路由** | 任务分发给哪个 agent | Dispatcher + Scheduler（dataflow ready queue） |
| **交换机** | 每端口独立冲突域 | **缩小争用粒度**（Z2 分区：每资源独立可写单元） |
| **多路复用** | 多条流共享信道 | 多 agent 共享一个工作区（靠分区 + 租约） |
| **CIDR 聚合**（**新增提议**） | 路由表压缩 | 按路径前缀聚合加锁（设计现状是单资源锁 + 路径字典序排序；前缀聚合需评估假冲突） |
| **ICMP（带内控制消息）** | 控制面与数据面分离 | Signal / Update / Query 三分离（**§10 已判定为不可迁移**：ICMP 与数据同信道，三分离是三个独立通道，不同构） |
| **TTL** | 防环路 | 租约 TTL（防僵尸持有者） |

**关键迁移**：

- **交换机的「每端口独立冲突域」** → 我们的 **Z2 分区**：**缩小争用粒度**（把共享总线拆成 per-resource 单元），**但不消除争用** —— RSC 仍会检出同一资源上的冲突（§5.2③：两个 agent 可能被同时准入写同一 Z2 资源，提交层裁决）。
- **CIDR 聚合**（**新增提议**）→ 按路径前缀聚合锁，减少锁数量；但会把锁粒度变粗、增加假冲突，需与单资源 CAS 语义权衡。
- **ICMP**（**带内**控制消息，承载于 IP）→ 控制消息（取消/审批/心跳）与数据消息（事件）分离，异步回报。

## 6. 介质争用：CSMA/CD ↔ 并发冲突

### 6.1 计网的答案

| 协议 | 机制 | 效率 |
|---|---|---|
| 纯 ALOHA | 想发就发，冲突随机重发 | 18.4% |
| 时隙 ALOHA | 时隙起点发 | 36.8% |
| CSMA | 先听后发 | 更高 |
| **CSMA/CD** | 先听后发 + **边发边听** + 冲突即停 + **二进制指数退避** | `1/(1+5a)`，其中 `a = τ / Tf`（单程传播时延 / 帧发送时延） |
| CSMA/CA | RTS/CTS 预约 + ACK（无线，难以检测冲突） | 开销大 |
| 令牌传递 / 信道划分 | 无争用 | 高 |

**CSMA/CD 关键**：争用期 = 2τ（τ = 单程传播时延）；最小帧长保证「发送时间 ≥ 争用期」，否则冲突无法被检测。

### 6.2 迁移到多智能体

| 计网概念 | 多智能体对应 | 我们的机制 |
|---|---|---|
| **CSMA（先听后发）** | 乐观并发：先尝试，冲突再处理 | RSC 的 prepare 阶段 |
| **CSMA/CD（边发边听）** | 提交时检测冲突（版本校验） | `ws.prepare`/`apply` 的 CAS |
| **冲突即停** | 冲突立即中止本次提交 | `CONFLICT` 返回 + rebase |
| **二进制指数退避** | 冲突后指数拉长重试间隔 | 重试退避（有界重试） |
| **争用期（2τ）** | **冲突窗口** | 租约 TTL（`LEASE_MS`） |
| **最小帧长** | ~~最小事务时长~~（见下：**反向对照**） | 计网用「发送时长 ≥ 争用期」换「冲突可检测」；我们**不用**这个机制 |
| **CSMA/CA（RTS/CTS）** | 无法检测冲突时的预约式协调 | 预留（IntentRegistry）+ 确认 |
| **令牌传递 / 信道划分** | 无争用 | 单写者串行档 + Z3 私有分区 |
| **交换机（独立冲突域）** | **缩小**争用粒度（非消除） | Z2 分区（每资源独立可写单元） |

> **反向对照（最小帧长，非可迁移）**：CSMA/CD 需要最小帧长，是因为**冲突信号要 2τ 才传回**，发送方必须「**仍在发送**」才能检测到冲突 —— 方向是「**越长越好**」。
>
> 而我们**不用**这个机制：冲突检测是 `ws.apply` 中**锁内原子复验** `base_version` + 读集合（§5.4，I1/I2），**与事务时长无关** —— 无论多短，冲突都会在提交时被检出。相反，设计 C1 / 原则 8 明确要求「**临界区必须短**」「锁不能跨 turn 持有」。
>
> **结论：两者方向相反。** 计网用「时长」换「可检测性」，我们用「短临界区 + 原子 CAS」换「可检测性」。这条只作**警示**（提醒我们：冲突检测机制的选择决定了事务时长约束），**不可迁移**。

## 7. 差错控制：CRC / 海明码 ↔ 校验与幂等

### 7.1 计网的答案

| 编码 | 检错 | 纠错 | 开销 | 适用 |
|---|---|---|---|---|
| 奇偶校验 | 奇数个错 | 无 | 1 bit | 粗校验 |
| **CRC** | 所有 ≤r 位突发、所有奇数个错 | 无（配 ARQ） | r bit | 以太网 FCS、存储 |
| 校验和 | 中等 | 无 | 固定位宽（通常 16 bit） | IP/TCP/UDP 首部 |
| **海明码** | 可检 2 位 | 纠 1 位 | r bit | ECC 内存、不可重传场景 |

**主流是「CRC 检错 + ARQ 重传」**；海明码只在「重传不划算/不可能」时用。

### 7.2 迁移到多智能体

| 计网概念 | 多智能体对应 | 我们的机制 |
|---|---|---|
| **CRC 检错** | 版本号/内容哈希校验 | `base_version` CAS、内容寻址 Artifact |
| **ARQ 重传** | 冲突后重试 | rebase + 有界重试 |
| **海明码（FEC）** | 不可重试场景的就地恢复 | 快照回滚（从最近快照重放） |
| **校验和（首部）** | 消息完整性 | 事件 `id` + hash-chain（收据） |

> **类比边界**：FEC 的关键是「**在消息里加冗余，接收方无需反馈即可纠错**」；我们的快照+重放是「**从检查点重算**」，更接近数据库 WAL + 崩溃恢复，且重放**不是「即时」**（要重放整段日志）。因此这是**类比而非等价**，落地时应按「长任务用快照兜底」理解，不要当成 FEC 的等价物。

**FEC vs ARQ 的权衡（最重要）**：

| 维度 | ARQ（重传） | FEC（前向纠错） |
|---|---|---|
| 开销 | 丢包稀少时极低 | **总是**付冗余 |
| 时延 | 至少 1 RTT | 即时恢复 |
| 适用 | 低延迟、可重试 | **高延迟、单向、不可重试** |
| 我们 | rebase + 重试（低延迟场景） | 快照 + 重放（长任务/单向场景，**非等价**） |

> **核心洞察**：**ARQ ≈ 我们的「冲突检测 + 重试」（低开销但需 1 RTT）；快照 + 重放 ≈ FEC 的「先做冗余工作」思路（但非等价，见上）**。选择依据是「agent 往返延迟」—— 短延迟用冲突重试式（ARQ），长延迟用快照兜底式。

## 8. 拥塞与流量控制：限流与背压

### 8.1 计网的答案

**关键区分**：

| | 流量控制 | 拥塞控制 |
|---|---|---|
| 保护对象 | **接收方**缓冲 | **网络**（队列/链路） |
| 机制 | 接收方通告窗口 | 慢启动/拥塞避免 AIMD |

**TCP 拥塞控制四阶段**：慢启动（指数）→ 拥塞避免（线性）→ 快重传 → 快恢复（乘性减）。
**AIMD**：加性增（公平收敛）+ 乘性减（快速退让）。

### 8.2 迁移到多智能体

| 计网概念 | 多智能体对应 | 我们的机制 |
|---|---|---|
| **流量控制（接收方窗口）** | 保护单个 agent 的上下文不被淹没 | 订阅过滤 + 上下文大小控制 |
| **拥塞控制（网络）** | 保护共享工作区/服务不被压垮 | `BudgetNode` 预算树 + 并发槽（`slots.available()`） |
| **滑动窗口** | 在途未确认消息上限 | 并发上限 + 老化 |
| **零窗口探测** | 防止反馈丢失导致死锁 | 心跳 + 租约超时 |
| **慢启动（指数增长）** | 冷启动时谨慎放量 | 准入预留（不阻塞）+ 按轮次逐步放量 |
| **AIMD** | 公平占用共享资源 | 老化（加性）+ OOM 式驱逐（乘性） |
| **AQM/ECN** | 网络主动发信号 | 事件总线主动推送冲突/版本信号 |
| **QoS（DiffServ 聚合）** | 分类保障 | 按任务优先级分类调度 |
| **令牌桶 / 漏桶** | 速率限制 | 队列级限速（设计 §14 P1） |
| **可靠多播** | 一对多可靠投递 | EventLog 的 fan-out + cursor（订阅者各自重放） |

> **核心洞察**：**流量控制 = 保护单个 agent 的上下文（订阅过滤 + 上下文大小）；拥塞控制 = 保护共享工作区（`BudgetNode` 预算树 + 并发槽）**。命名区分很有价值，避免混淆。

## 9. 设计思想迁移

### 9.1 端到端原则（最重要，但要分清「机械一致性」与「语义正确性」）

**计网**：正确性/可靠性/安全应放在**端系统**，网络只做尽力而为传输。

**迁移（关键澄清）**：端到端原则**不是**说「共享层什么都不保证」，而是说「**语义正确性**应由理解语义的一方判定」。对应到我们：

| 层次 | 谁负责 | 内容 |
|---|---|---|
| **共享层（中间）** | IntentRegistry / WorkspaceManager / EventLog | **机械一致性**：fencing、CAS、版本线性化、事件不丢（I1/I2/I8） |
| **独立验证器** | VerifierRunner（独立上下文，不共享生成器轨迹） | **语义正确性**：test/lint/契约/覆盖度 |
| **端点策略** | agent 自身 | 局部决策（是否重试、如何 rebase） |

> **与设计的张力（必须正视）**：严格端到端原则会主张「网络只做尽力而为」，而我们**恰恰在共享层提供机械正确性**（§0.2 差异化第 1 条；Z2 线性化；I1/I2）。这不是矛盾，而是**分工不同**：
> - 计网的「可靠性」是**语义无关的字节可靠**（TCP 不懂 HTTP）；
> - 我们的「机械一致性」是**语义无关的写冲突正确**（RSC 不懂任务语义）。
>
> 所以正确的表述是：**共享层提供「语义无关的机械一致性 + 信号」，VerifierRunner 与端点提供「语义正确性」**。这与设计 §8（VerifierRunner 独立上下文、不信任 agent 自评）一致。

**例外**：性能考虑（缓存、CDN）—— 我们的物化快照就是「性能例外」。

### 9.2 FEC vs ARQ 二分法

**计网**：低 RTT 用 ARQ，高 RTT/单向用 FEC。

**迁移**：
- **低延迟**（agent 往返快）→ ARQ 式：冲突检测 + 重试（RSC）。
- **高延迟/长任务** → FEC 式：快照 + 重放（checkpoint + 重放）。
- **混合**：链路层 FEC + 传输层 ARQ → 我们的「快照兜底 + 冲突重试」。

### 9.3 无状态 + 命运共享

**计网**：IP 无状态（可扩展）；命运共享（状态随连接消亡，避免孤儿状态）。

**迁移（区分两类状态）**：

| 状态类型 | 命运 | 例子 |
|---|---|---|
| **短暂协调状态** | **随会话共存亡**（命运共享） | 订阅关系、租约、cursor |
| **持久状态** | **故意存活**（可复制） | EventLog 事件、Checkpoint |

- **转发层无状态**：SubscriptionRegistry 只做路由，不保存会话状态。
- **短暂状态随会话消亡**：agent 崩溃 → 租约回收 + **订阅关系标记失效**（下次 `context_view` 时按需重建）；**cursor 从 checkpoint 续放**（不重置 —— 重置会导致全量重放）。
- **持久状态外置**：一致性状态放 EventLog/CheckpointStore（可复制），不散落在各组件。

> **注意**：这两类状态的「命运」相反 —— 短暂状态随会话消亡（命运共享），持久状态故意存活（可恢复）。计网用「连接」统一了两者的边界；我们用「会话」与「Run」区分。

### 9.4 尽力而为 + 叠加

**计网**：核心只做一件事，可靠性按需叠加（洋葱式）。

**迁移**：
- **核心最小**：IntentRegistry + WorkspaceManager 只做「版本 + 租约 + CAS」。
- **按需叠加**：需要更强一致性时，叠加快照/重放；不需要时不付代价。

### 9.5 分层与窄腰

**计网**：窄腰（IP）让上下独立演化。

**迁移**：
- **窄腰 = 资源提交层**：唯一必须全局一致的契约（资源 ID + 版本 + 租约）。
- 上层（任务语义）与下层（存储介质）可独立演化。

### 9.6 协议即契约

**计网**：协议 = 双方共同遵守、可独立演进的消息契约（LSP/MCP 都是这个思想）。

**迁移**：我们的「协调协议」（声明意图 → 获取租约 → 提交/释放）就是 agent 生态的「窄腰协议」。

## 10. 可迁移机制清单（按价值排序）

| # | 机制 | 来源 | 迁移形态 | 收益 | 难度 |
|---|---|---|---|---|---|

| 2 | **FEC/ARQ 二分** | 计网可靠性 | 低延迟用冲突重试；长任务用快照重放 | 极高 | 中 |

| 10 | **协议即契约** | 体系结构 | 协调协议 = agent 生态的窄腰协议 | 高 | 低 |

## 11. 明确不可迁移的

| 计网机制 | 为何不可迁移 | 替代方案 |
|---|---|---|
| **物理层的信号/编码**（曼彻斯特、调制） | agent 不走电信号；无物理介质约束 | 用「逻辑序号 + 版本」替代「时钟同步」 |
| **真正的广播/组播**（信道共享） | agent 通信是消息传递，不是共享信道 | 发布订阅（逻辑组播） |
| **电路交换**（专用通路） | 无法为每个 agent 预留专用带宽 | 预留（逻辑预约）+ 统计复用 |
| **全局时钟同步**（NTP） | agent 时钟不可信 | 逻辑时钟 + 中心序列器 |
| **硬件 CRC** | 无硬件 | 版本号 + 内容哈希（软件） |
| **IP 分片/重组** | agent 消息无 MTU 分片需求（有 token 上限但不同） | 消息分块 + 引用（ArtifactRef） |
